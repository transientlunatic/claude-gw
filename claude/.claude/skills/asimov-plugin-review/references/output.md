# Review output

Every review produces **both** outputs below, from the same list of verified
findings.

## 1. Structured report

Write two files into the plugin repository's `review/` directory (create it;
don't commit it unless asked):

- `review/asimov-plugin-review.json`: machine-readable, for the session that
  fixes the plugin.
- `review/asimov-plugin-review.md`: human-readable.

### JSON

```json
{
  "plugin": "asimov-jim",
  "commit": "<git rev-parse HEAD>",
  "asimov": {"ref": "v0.8-preview", "commit": "<sha>", "vocabulary": true},
  "verdict": "changes-required",
  "summary": "One paragraph: the overall shape of the plugin and the main themes.",
  "findings": [
    {
      "id": "F1",
      "rule": "AP-LEDGER-001",
      "severity": "BLOCKER",
      "file": "asimov_jim/pipeline.py",
      "line": 98,
      "title": "PSDs read from jim: data: psd_files instead of psds",
      "evidence": "\"psd_files\": dict(jim_data_meta.get(\"psd_files\") or {}),",
      "core_reference": "asimov/analysis.py:Analysis._collect_psds; vocabulary term `psds`",
      "why": "Duplicates a standard quantity and skips PSD hand-off from upstream `needs:` analyses.",
      "fix": "Read self.production.psds; drop jim: data: psd_files from code, README and examples.",
      "source": "lint"
    }
  ],
  "upstream": [
    {
      "title": "Generic GPU requests in JobDescription",
      "existing_issue": "etive-io/asimov#161",
      "evidence": ["asimov_jim/pipeline.py:346"]
    }
  ],
  "dismissed": [
    {"rule": "AP-NORM-004", "file": "asimov_jim/pipeline.py", "line": 361,
     "reason": "Dry-run plan output; print is appropriate."}
  ],
  "checked_by_hand": ["AP-CORE-010", "AP-CORE-013", "AP-TMPL-004"]
}
```

- `verdict` is `changes-required` if there is any BLOCKER or MUST-FIX;
  `approve-with-upstream` if there are only SMELLs (and NITs); otherwise
  `approve`.
- `source` is `lint` (a confirmed linter candidate) or `review` (found by
  reading).
- Every linter candidate ends up in either `findings` or `dismissed`, never
  silently dropped.
- `checked_by_hand` lists the non-lint rules you actually checked.

## 2. PR review comments

Only when the review was given a pull request (number or URL).

1. Create a pending review with `mcp__github__pull_request_review_write`
   (`method: create`).
2. For every BLOCKER and MUST-FIX finding whose line is part of the PR diff,
   add an inline comment with `mcp__github__add_comment_to_pending_review`,
   formatted as:

   ```
   **[BLOCKER] AP-LEDGER-001: PSDs read from `jim: data: psd_files` instead of `psds`**

   <why, 1–3 sentences, naming the core feature it duplicates>

   Fix: <concrete change>
   ```

   Findings on lines outside the diff, SMELLs and NITs go only in the review
   body.
3. Submit with `method: submit_pending`, event `REQUEST_CHANGES` if the
   verdict is `changes-required`, otherwise `COMMENT`. Never `APPROVE`: a
   human approves.
   The review body is the Markdown report's verdict line, summary and a
   compact list of all findings (ID, severity, title, location), followed by:

   ```

   ---
   _Generated by [Claude Code](https://claude.ai/code)_
   ```

Don't post anything to GitHub unless the caller asked for PR comments or
passed a PR. A review of a local checkout produces only the files.
